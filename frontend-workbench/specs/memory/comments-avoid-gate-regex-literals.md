title: 注释里写"禁止的字面量"要用转述，避免被门禁正则误判为违规
feature: 3.workbench-app-scaffold
type: pitfall
tags: [documentation, comments, gate, regex, false-positive, quality-gates]

---

**问题/场景**：`client-context.tsx` 顶部注释写"⛔ 组件层禁止 `new MastraClient(` /
`fetch(` / `axios`……不得配置任何被禁端口（8000/8001/8002/6333/8787/11434）"——这是在
**说明规则**，逻辑代码里完全没有这些调用。但 Feature 8 的直连门禁是纯文本
`grep -rnE ':(8000|8001|8002|6333|8787|11434)|getAgent\(' web-client/src`，扫描
整个源码文本（含注释），无法区分"代码里调用了" vs "注释在提醒别调用"，会把这条
说明规则的注释误判为违规命中。

**解法/结论**：本次选择改注释、避开这些字面量（用"组件层禁止绕过 useClient()
自行发起网络请求或直连其他后端服务"这种转述），逻辑代码不动。这是两种可能修法
里成本最低的一侧——另一种修法是让门禁扫描脚本本身排除注释/字符串字面量（更复杂，
且会影响 Feature 8 的实现，本 feature 阶段不适合展开）。

**复用方式**：
1. 在本项目里，写文档/注释提醒"禁止使用 X"时，如果 X 是某个已知门禁正则会匹配的
   字符串（端口号、危险函数名如 `fetch(`/`axios`/`new MastraClient(`/`getAgent(`），
   优先用转述描述规则，不要在注释里直接写出这些字面量；
2. Feature 8（`quality-gates-and-design-review`）实现门禁扫描脚本时，应当**意识到
   这类假阳性来源**：决定是否要给扫描脚本加"排除注释行/字符串字面量"的逻辑，
   还是继续要求全仓库注释都用转述规避——两种都是合法选择，但要在 Feature 8 的
   design.md 里明确写清楚选了哪种，不要含糊；
3. 如果未来新增被禁端口/API（比如需求变更引入新的禁连服务），同步检查现有代码库
   注释里有没有已经"合法但会被新规则误伤"的说明性文字。
