**问题/场景**：`contract-mirror.test.ts` 用手写正则/字符扫描（而非 TypeScript AST）实现"两个包之间的类型镜像一致性检查"，五轮 Codex Review 依次揭穿了同一个手写解析器的四层不足：①只比字段名，漏掉类型/可选标记本身的漂移；②比了类型字面量，但没解析被引用的别名/接口的真实定义，漏掉"引用名相同但定义已漂移"；③按换行切分字段，遇到合法的多行类型声明会静默丢字段（最危险的情况是两侧都用同一种多行写法、都被丢弃，测试反而"通过"）；④用字符计数模拟括号深度时，把 `=>`（箭头函数类型）的 `>` 误当泛型收尾，导致深度计数出错、后续字段被错误合并。

**解法/结论**：如果决定手写解析（而不是接入 TS Compiler API 的真实 AST），预先针对以下四层做检查，不要等 CR 一轮轮揭穿：
1. **不要只比字段名**——同时比较可选标记（`?`）与类型表达式文本。
2. **解析被引用的别名/接口，不要只比引用名字符串**——`type X = ...` 或跨文件 `interface`，都要能被解析展开成真实定义再参与比较。
3. **按"顶层分隔符"（如分号）切分语句，不要按换行切分**——类型表达式允许合法跨多行，追踪括号/花括号/尖括号深度，深度为 0 的分隔符才是真正的语句边界。
4. **每种"看起来像括号但其实不是"的符号单独处理**——`=>`、字符串/注释里的括号、正则字面量等，都可能让"用字符计数模拟嵌套深度"的简化方案算错。

**复用方式**：任何"要在两个不共享编译单元的包之间做类型/契约一致性检查"的场景都会遇到同样的选择题。窄场景（少量 flat interface + 简单 union 别名，未来复杂度增长有限）可以接受手写解析器，但要按上面四层预先加固；一旦契约类型开始出现嵌套泛型、条件类型、映射类型，维护手写解析器的成本会迅速超过直接用 `typescript` 包的 `ts.createSourceFile()` 遍历 AST 的成本，应该尽早切换，不要在手写方案上持续打补丁。验证解析器改动是否真的修复问题的低成本手段：用 `fs.writeFileSync` 写一份"故意改错"的源码到临时文件跑同一个提取函数，比搭建 mock 测试夹具更快，验证完删除临时文件即可。
