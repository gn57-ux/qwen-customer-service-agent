## 2. 职责边界（数据设计的第一原则）

按两份设计方案与后续补充约束，本数据集严格区分四层职责：

```text
System Prompt → 身份、规则、越权边界
QLoRA        → 客服语气、回复结构、意图识别、澄清追问、安全边界、处理流程、拒答与升级习惯
RAG          → 维修文档、售后政策、退款规则、物流规则、产品参数等可更新事实
Tools/API    → 订单、物流、退款进度等实时状态（queryOrderTool）
```

### 2.1 QLoRA 学到什么

- 先判断意图，信息不足先追问，再给可执行的下一步；
- 缺订单号时索要订单号，有订单号时表达“需要调用订单系统查询”；
- 政策类问题表达“需要检索知识库/以现行条款为准”，不背诵条款数字；
- 工具或知识库失败时明确说明**无法确认**，给重试与转人工路径；
- 危险维修操作一律拒绝，并给断电、远离、联系专业售后的安全动作；
- 超出权限（赔付、换机、特批、加急）时说明原因并升级人工。

### 2.2 QLoRA 明确**不**学什么

| 禁止作为模型知识 | 本数据集的处理方式 |
|---|---|
| `ORD1001` / `ORD1002` / `ORD1003` 的固定状态 | 这三个订单号 + `ORD9999` **完全不出现**在 800 条中，审计第 15 项强制拦截；它们只保留在 Mock 后端与 `agent-tool-evaluation.json` |
| 固定物流节点、预计送达日期 | 无任何绝对日期、承诺时长；审计第 16 项用正则拦截 `2026-07-25`、`X月X日`、`预计N天内送达`、`已到达XX转运中心` 等断言 |
| 固定退款进度 | 退款样本只训练“查系统 / 说环节 / 不给到账日”的行为 |
| 具体保修年限、退货天数、上门费金额 | 统一表达为“按型号与现行条款核对后答复”，不写死数字 |
| 具体维修网点、产品详细参数 | 统一表达为“需检索产品资料 / 按型号核对” |

### 2.3 工具返回的表达方式（重要设计决定）

要训练“Tool 成功后依据返回内容组织回复”，就必须让模型见到工具输出。
由于本数据集格式被限定为 `system / user / assistant` 三角色（不引入 `observation` 角色，
以保持与现有 20 条冒烟数据和 `dataset_info.json` 的 ShareGPT 配置完全兼容），
工具返回以**带标记的用户轮**注入：

```text
user:      订单 ORD5088 现在什么情况？
assistant: 我用 ORD5088 去订单系统查询当前状态，请稍等。
user:      [订单系统返回] found=true, order_id=ORD5088, status=paid,
           status_text=已付款待出库, carrier=null, tracking_number=null,
           estimated_delivery=null
assistant: 查到了：这笔订单目前处于已付款待出库，系统里还没有承运方和运单号，
           也没有给出预计送达时间，所以我不替它估日期。……
```

共 13 条样本采用该结构，覆盖 `found=true`、`found=false`、`timeout`、
`http_500`、`http_503`、`connection_refused`、`field_missing`，以及
`[知识库检索] 未命中相关条款` 的 RAG 降级。要点：

- 块中的取值**每条都不同**，不构成可记忆的静态事实；
- assistant 只转述块内已有字段，字段为空即明确说“系统没有给出”；
- 审计第 16 项对**不含该块**的样本才判定编造，含块样本的转述属于有依据表达。

### 4.1 关于第 10 项 WARN

审计对危险关键词采用**分句判定**：
句中出现 `拆机 / 后盖 / 高压 / 压缩机 / 制冷剂 / 电源板 / 带电 / 短接 / 排线 / 电路图` 等词时，

- 同句含禁止或风险表述（`不要 / 请勿 / 严禁 / 不能 / 失去保修 / 风险` 等）→ 合规；
- 同句含指导性引导语（`请先 / 可以先 / 建议您 / 教您 / 按以下步骤` 等）且无禁止表述 → **判 FAIL**；
- 两者都没有 → 计入说明性提及，仅告警。

当前 19 处说明性提及全部经人工确认为正当表述，例如：

- `压缩机运转时有没有声音` —— 让用户用听觉描述现象，不涉及接触；
- `液晶电视的电源和主板都靠机身背部散热` —— 解释发热属正常；
- `我先给免拆机的自查项` —— 明确限定在免拆范围；
- `涉及拆卸和复原的责任划分，我一并登记由人工审核` —— 谈责任归属，不是操作指导。

### 5.3 复查发现并修复的问题

1. **`rr-tr-x08` 转述超出工具返回**
   工具块给的是 `refund_status=processing, refund_stage=待财务打款`，
   原 assistant 写成“这笔退款**已通过审核**，目前在待财务打款环节”——
   “已通过审核”是从阶段名推断出来的，超出了返回内容。
   已改为“系统返回的是处理中，当前停在待财务打款环节……也不替它推断已经审核到哪一步”。

2. **`wa-va-08` 元数据与内容不符**
   该样本第一轮陈述安装收费规则（应属 RAG），第二轮用订单号核对标准安装范围（应属 Tool），
   但 `requires_rag` / `requires_tool` 都是 false。已改为 `rt`。

3. **`sr-te-03` 混用半角标点**
   `也不要用水扑;人和易燃物离开设备` 中出现半角分号。已改为句号并重写该句。
   同时补充了一条全量扫描，确认 800 条中已无半角 `, ; ! ?` 与半角括号。

## 6. 质量控制手段

| 风险 | 控制手段 |
|---|---|
| 机械套模板 | 逐条人工撰写，无模板批量生成；审计第 19 项校验开头多样性（当前最高 2.3%） |
| 伪多样性（只换品牌/型号/订单号） | 型号仅在确有必要时出现且不构成主要差异；每条样本的问题情境、排查路径与表达结构各不相同 |
| 句式重复 | 880 条 assistant 回复中有 737 种不同开头；全量 assistant 文本零重复 |
| 测试集泄漏 | 每条样本显式声明 split；审计第 7/8/12 项做精确与近似重复检测，跨 split 最高相似度未进入 0.58 告警区间 |
| 编造事实 | 审计第 16 项正则拦截；动态事实只能来自对话内的工具返回块 |
| 隐私 | 无姓名、手机号、证件号、邮箱、银行卡号、详细地址；样本中多处**主动拒绝**用户发送敏感信息 |
| 危险维修指导 | 审计第 10 项分句判定；`safety` 版 system prompt 覆盖 85 条高风险样本 |
| 数据漂移 | 审计第 20 项做源模块与 JSON 的往返一致性校验，任何手改 JSON 都会被发现 |

## 8. 建议的下一步

1. **不要立刻开训**：先在 4090 上跑一次 `llamafactory-cli train` 的数据预处理（`do_train: false` 或极小 `max_steps`），
   确认 `qwen3_nothink` 模板下 640 条的 token 长度分布，再决定 `cutoff_len` 是否需要从 1536 上调。
2. **补齐 RAG 侧**：本数据集有 106 条样本表达“需要检索知识库”，但 `knowledge/` 下的
   冰箱/彩电/显示器维修 MD 与 SOP、退款、物流规则文档尚未建立。QLoRA 训练可以先行，
   但端到端效果依赖这批文档入库。
3. **接线 Agent 评测**：`datasets/agent-tool-evaluation.json` 的 12 个用例需要一个 runner
   来驱动 Mastra Agent，并在 Mock 后端上注入 `timeout` / `http_500` / `field_missing` 三种故障态
   （当前 `services/mock_backend.py` 只实现了正常与 404）。这属于服务侧改造，本次未触碰。
4. **固定评测口径**：`customer-service-test-80.json` 建议配一个打分脚本，
   按 SOP 合规率、澄清追问率、无依据拒答率、高风险拦截率四项出 Base vs QLoRA 对比报告。
5. **数据集版本绑定**：训练启动时把本报告中的三个 SHA-256 写进
   `training/registry/customer-service-v2.yaml` 的 `dataset_version` 旁，保证可追溯。
6. **后续扩量方向**（如需 1000 条以上）：优先补 `multi_intent`（当前 69）与
   `unverifiable`（当前 70）两类，它们在真实会话里占比高于当前配比。
